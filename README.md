# CineOS — Autonomous AI Movie Production Studio

Enter a movie idea, genre and duration. Four specialised AI agents (Producer, Story, Character and Screenwriter) collaborate to produce a production plan, story, cast, screenplay and scene breakdown, all persisted in MongoDB and shown in a React dashboard.

**Stack:** React + TypeScript + Vite · Node.js + Express 5 + TypeScript · MongoDB + Mongoose · Google Gemini, free tier (`@google/genai`) · Docker Compose

## Quick start

Requirements: Node.js 22+, npm, Docker, FFmpeg (`ffmpeg` + `ffprobe`) for video rendering.

```bash
cp .env.example .env          # add a free GEMINI_API_KEY for real AI output (optional)
npm install
npm run infra:up              # MongoDB on localhost:27018
npm run dev                   # API on :4000, dashboard on http://localhost:5173
```

Production build (the API also serves the built dashboard on :4000):

```bash
npm run build && npm start
```

## LLM modes

| `LLM_MODE` | Behaviour |
| --- | --- |
| `auto` (default) | Gemini when `GEMINI_API_KEY` is set, otherwise mock |
| `gemini` | Always Gemini; startup fails without a key |
| `mock` | Deterministic mock output, no API calls |

Every generated document has a `provenance` field (`provider`, `model`, `isMock`). The dashboard labels mock content **MOCK · not AI-generated** and Gemini content **Generated by Gemini · &lt;model&gt;**. Mock text is also prefixed with `[MOCK]`. `GET /api/health` reports the active mode.

**Free Gemini key:** create one at <https://aistudio.google.com/apikey>; the free tier needs no billing. Free-tier limits apply (a 429 response means you have hit the rate limit or daily quota, so wait and retry), and Google may use free-tier prompts to improve its products, so don't enter private data.

Settings: `LLM_MODEL` (default `gemini-4-hydrogen`; any model available on your tier) and `LLM_MAX_TOKENS` (default `16000`).

## Architecture

```
frontend (React) ──/api──▶ Express routes ──▶ services ──▶ Mongoose models ──▶ MongoDB
                                  │
                                  └─▶ ProductionWorkflow ──▶ Producer → Story → Character → Screenwriter
                                                                   │ (all agents)
                                                                   ▼
                                                     LlmClient (shared): Gemini | Mock
```

- **Agents** (`backend/src/agents`): each one has its own responsibility, system prompt, typed input, Zod output schema and deterministic mock builder. All of them call the model through the single `LlmClient`.
- **Producer coordination:** the Producer's plan sets the creative direction and writes one brief for each downstream agent, plus the Screenwriter's target scene count. The workflow passes each brief, and every upstream output an agent depends on, to that agent.
- **Structured output:** each agent's Zod schema is converted to JSON Schema and sent to Gemini as `responseJsonSchema` (JSON mode). The response is then validated against the same Zod schema. Mock output is validated against the same schemas too.
- **Generation:** `POST /api/projects/:id/generate` returns `202` and runs the workflow in the background. Per-agent status (`pending → running → completed / failed / skipped`) is stored on the project and polled by the dashboard.

## Media processing (FFmpeg)

Requires `ffmpeg` and `ffprobe` on the server (`sudo apt-get install -y ffmpeg`). If they are missing, `GET /api/health` reports `media.ffmpeg: false`, render requests return `503 FFMPEG_UNAVAILABLE` with the install command, and nothing is ever mock-rendered.

From a production's **Video & trailers** tab (or `POST /api/projects/:id/renders`) you can render:

- **Film**: the selected scenes as an animatic. Each scene's length follows the screenplay's estimate, scaled to the target length (default ~45 s). The film has a title card, an end card and a dialogue caption per scene.
- **Trailer**: up to 6 scenes in short 2.5–4 s cuts, with a hook card, a logline card, a title reveal and a "coming soon" card. It is a separate MP4 with its own version. It records the film whose scene visuals it reuses (`sourceRenderId`), and every scene's versioned creative-memory asset.

The pipeline (`backend/src/media/`) runs on the BullMQ `cineos-render` queue in the worker process:

1. **Scene visuals.** It uses `media/library/<projectId>/scene-<n>.(png|jpg|jpeg|webp)` if FFprobe can decode it. Otherwise it generates a scene card (PNG). Cards are content-addressed, so later renders and trailers reuse them.
2. **Segments.** Each segment is encoded as an H.264 clip: title cards from a lavfi colour source, scenes from their still with a push-in, captions and fades.
3. **Join.** Clips are joined with the concat demuxer.
4. **Audio.** One of three modes: `score` (synthesised by FFmpeg `aevalsrc`), `library` (`media/library/<projectId>/soundtrack.*`, looped/trimmed; missing → `400`) or `none` (no audio track, recorded explicitly).
5. **Validation.** The result is checked with FFprobe: H.264, yuv420p, AAC when audio was requested, duration within 0.5 s of the plan, `moov` before `mdat` (`+faststart`). Only then is it moved into storage.

FFmpeg always runs via `spawn()` with argument arrays and no shell. Scene/LLM text reaches `drawtext` through `textfile=` + `expansion=none`. Each attempt uses its own scratch dir under `media/tmp/`, which is always removed afterwards. Interrupted renders are picked up again: by BullMQ's stalled-job check if the worker dies, and by the API on startup if Redis lost the job.

Progress flows worker → `job.updateProgress` → Redis → `QueueEvents` in the API → Socket.IO (`render:queued|started|progress|completed|retrying|failed` in the project's room). It is mirrored to the `mediarenders` collection: status, stage, progress, scenes, inputs, audio, output path and FFprobe metadata, errors, timings.

Files: `media/projects/<projectId>/renders/<renderId>.mp4` (served at `/media/…` with HTTP Range support) and `media/projects/<projectId>/visuals/`. Settings: `MEDIA_ROOT`, `FFMPEG_PATH`, `FFPROBE_PATH`, `RENDER_CONCURRENCY`, `RENDER_TIMEOUT_SECONDS`.

## REST API

| Method & path | Description |
| --- | --- |
| `GET /api/health` | API, MongoDB and LLM mode |
| `GET /api/agents` | The four agents and their responsibilities |
| `POST /api/projects` | Create a project `{ title, idea, genre, durationMinutes }` |
| `GET /api/projects` | List projects |
| `GET /api/projects/:id` | Get a project |
| `POST /api/projects/:id/generate` | Start generation (`202`; `409` if already running) |
| `GET /api/projects/:id/status` | Generation and per-agent status |
| `GET /api/projects/:id/plan` | Production plan |
| `GET /api/projects/:id/story` | Story |
| `GET /api/projects/:id/characters` | Characters |
| `GET /api/projects/:id/screenplay` | Screenplay with its scenes |
| `GET /api/projects/:id/scenes` | Scenes |
| `POST /api/projects/:id/renders` | Render `{ kind: film\|trailer, sceneNumbers?, targetSeconds?, audio: score\|none\|library }` (`202`) |
| `GET /api/projects/:id/renders` | Media history for a production |
| `GET /api/renders/:id` | One render (status, progress, inputs, output metadata) |
| `GET /api/renders/:id/download` | Download the MP4 |

Errors use the shape `{ "error": { "code", "message", "details?" } }` (`400` validation, `404` not found or not yet generated, `409` conflict).
